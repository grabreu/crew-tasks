# Access to a list is checked in the handler's query, by membership

Every list and item slice resolves access through the user's membership inside the query itself: lists are read through `TodoListMemberships`, items through `TodoItem.TodoList.Memberships`, and a collection only contains rows the user may see. A user who is not a member gets the same 404 as for a record that does not exist, so a list's existence is not revealed, and the database never returns the row. The rules that depend on a role (only the owner deletes a list, manages invites, or removes other members) are checked in the handler after loading the user's membership: not a member responds 404, a member who is not the owner responds 403.

Considered and not adopted: ASP.NET Core resource-based authorization (`IAuthorizationService`), tried on the item endpoints with an attribute implementing `IAuthorizationRequirementData`. It took five files and about 100 lines to replace a one-line predicate, queried the membership and then the item again, needed a global `IAuthorizationMiddlewareResultHandler` to answer 404 instead of 403, ran its handler for anonymous requests, and ran before the body was validated. It also resolved the list from the item id in the route or from the body, depending on the endpoint, since the body is bound after endpoint authorization.

**Consequences**: the membership predicate is repeated in each slice, one line each, and a new slice must include it: nothing enforces it, and there are no automated tests yet to catch a slice that does not. Owner-only operations repeat a few lines (load the membership, 404, 403). Revisit if roles beyond owner and member appear, if rules start depending on item state (assignee, due date), or if several entry points need the same non-trivial rule.

# Modules query each other through interfaces in `*.Contracts`

Events remain how modules react to each other. When a module needs data owned by another one, it calls an interface declared in the owner's `.Contracts` project, implemented inside the owner module and resolved through dependency injection. The call is in-process and synchronous; the caller references only the contracts project, never the other module's internals.

The first one is `IUserDirectory` (`CrewTasks.Users.Contracts`): it resolves user ids to display name and email in one batch call. Todos uses it to put display names in the member list; Notifications uses it to find the list owner's email for the member-joined message. Todos only knows `UserId`, and the data lives in the Users schema, so a join is not possible (no foreign keys across schemas, see ADR 0003). The email is returned to in-process callers only; no Todos endpoint exposes it.

Considered and not adopted:
- A local replica in Todos (a table with id, display name, and email), fed by events from Users (user created, user onboarded). It is a sound option: the name is set once at onboarding and the email is the login identity, so staleness is not a concern today; member lists would be a local join; and the notification event could carry the data it needs. Not adopted because the users that already exist produce no event, so it needs a backfill; Users and Todos save in separate contexts with no outbox, so a failed handler leaves a user missing from the replica with nothing to repair it; the email would live in a second schema and in events; and it is more code (two events, two handlers, an entity, a migration) for a monolith that shares one database.
- Carrying the data in events alone: it does not help when the recipient is someone other than the actor (for example the list owner when a member joins).
- A Mediator query declared in `*.Contracts`: equivalent, with an extra layer of indirection for a lookup that is not a use case.

**Consequences**: a lookup fails together with its caller, since there is no network between them. Callers must handle ids with no match (a user that no longer exists) and use the batch call instead of one lookup per row. Each new interface of this kind widens what a module exposes, so it belongs in `.Contracts` only when events do not fit. Revisit the replica if a module is split into its own service, if the lookup becomes a bottleneck, or if profile or email editing appears.
